# 솔라스 서평 엑셀 대조 및 거리 반영

2026-10-30 구현. 프론트 디자인은 cf34ff0 기준으로 복원했으며 기존 스타일을 재사용한다. 업로드·대조·관리자 확인 기능을 `/admin/reviews`에 연결했다. 별도의 도서관 API나 자동 로그인을 사용하지 않는다.

## 운영 절차

1. 관리할 행사를 선택한다. 솔라스에서 받은 xlsx 파일을 업로드한다.
2. 업로드만으로 쪽수·거리·서평 확인 상태는 변경되지 않는다.
3. 각 행에서 회원번호, 도서 ID, 도서명, 서지 정보, 서평 제목·본문, 최종 수정일을 확인한다.
4. 후보가 여러 개면 실제 참가 도서를 선택한다. 제목 대조·이름 차이·기간 밖 수정일 등 추가 확인 항목에는 검토 메모를 필수로 입력한다.
5. 작성자·도서·서평 내용·행사 인정 기간을 확인했다는 체크 후 거리 반영을 누른다. 서버가 승인된 쪽수 중 아직 인정하지 않은 부분만 1쪽당 5m로 반영한다.
6. 확인 관리자·시각·반영량이 남는다. 업로드 내역은 다시 열 수 있으며 20개씩, 원본 행은 50개씩 조회한다.

사용자 본인의 작성 완료 체크는 거리 인정의 조건이 아니다. 엑셀 근거를 관리자가 확인하면 자기 신고 없이도 반영된다. 완독 전의 일부 독서도 인정하며, 서평 미작성 때문에 다음 독서일지가 제한되지 않는다.

## 지원 양식 및 대조 규칙

- 1개 시트, 첫 행의 열 순서: `ID`, `TITLE`, `ETC_CONTENT`, `MEMBER_NO`, `NAME`, `TITLE_1`, `CONTENT`, `LAST_UPDATED`.
- 5MB 이하, 데이터 최대 2,000행, 원문 총 4,000,000자 이하. 수식·오류 셀은 실행하지 않고 오류 행으로 표시한다. 파일 구조·헤더 오류는 업로드 자체를 거절한다.
- 회원번호는 문자열이다. `MEMBER_NO`와 사이트 `studentNo`가 정확히 같은 참가자만 찾는다. 이름만으로 연결하지 않는다. 서로 다른 번호 체계라면 운영자가 번호 매핑 정책을 정해야 하며 현재 임의 보정은 없다.
- `ID`는 솔라스 `biblio.id`로, 사이트 `libraryBookId`와 비교한다. 등록번호나 ISBN으로 간주하지 않는다.
- 회원번호+도서 ID를 우선하며 ID 일치가 없을 때 같은 회원의 정규화된 제목 일치 후보를 제공한다. 제목 후보는 관리자가 판본을 확인하고 메모해야 한다. `ETC_CONTENT`는 서지 정보 참고용이며 ISBN으로 해석하지 않는다.
- `LAST_UPDATED`는 최종 수정일이며 최초 작성일이나 제출일이 아니다. 접수기간 밖이면 경고하지만 자동 인정·자동 탈락하지 않는다. 원문 작성 시점과 행사 인정 규칙을 담당자가 별도 확인하고 메모한다. 시각은 솔라스의 로컬 시각으로 취급한다.
- 취소·실격, 승인 독서 기록 없음, 미인정 쪽수 없음, 자료 오류는 반영할 수 없다. 최종 확정·보관 행사는 업로드와 반영을 차단한다.

## 중복 및 동시 처리

파일 해시는 이력 추적용이다. 중복 인정 방지는 행사 + 회원번호 + 도서 ID + 정규화된 본문으로 만든 근거 해시와 DB 유일 제약으로 처리한다. 수정일이나 서평 제목만 바뀌어도 동일 본문은 새 근거가 되지 않는다. 같은 근거의 재요청은 `alreadyApplied: true`와 기존 이력을 반환하며 추가 거리는 0이다.

추가 독서량에는 기존에 반영한 본문을 재사용할 수 없다. 새 본문이더라도 해당 도서에서 마지막으로 인정한 엑셀 근거보다 수정 시각이 같거나 이전이면 반영 후보에서 제외한다. 승인된 쪽수·미인정 쪽수는 미리보기 값과 최종 요청 값을 비교한다. 변경됐다면 `REVIEW_TOTALS_CHANGED`로 거절하고 새로 조회한다. 기존 독서일지 승인과 같은 참가자 단위 DB 잠금으로 수동 확인·동시 관리자 작업과의 중복 누적을 방지한다.

## API

모든 경로는 `/api/admin/review-imports` 아래이며 ADMIN/SUPER_ADMIN 전용이다. 응답은 기존 `{success, code, message, data}` 형식이다. 모든 요청에 `eventId`가 필요하다.

| 요청 | 용도 |
|---|---|
| `POST ?eventId=1` | `multipart/form-data`, `file` 필드. 업로드 배치 반환 |
| `GET ?eventId=1&page=0` | 배치 이력 20개씩 |
| `GET /{batchId}?eventId=1&page=0` | 원본 행·대조 후보·경고·기존 반영 이력 50행씩 |
| `POST /{batchId}/rows/{rowId}/confirm?eventId=1` | 관리자가 선택한 후보를 확인하고 거리 반영 |

최종 확인 JSON 예:

```json
{"participantBookId":9,"expectedApprovedPages":200,"expectedUncreditedPages":50,"evidenceChecked":true,"note":"도서관 원문과 판본 확인"}
```

행 상태: `MATCHED`, `NEEDS_REVIEW`, `UNMATCHED`, `INVALID`, `NO_CREDIT`, `ALREADY_APPLIED`.

확인 응답: `id`, `participantBookId`, `creditedPages`, `creditedDistanceMeter`, `verifiedBy`, `verifiedAt`, `alreadyApplied`. 이미 처리한 요청의 인정량은 과거 반영량을 뜻하므로 화면에서 새 합산에 사용하지 않는다. 조회 API로 현황을 갱신한다.

## 저장 및 배포

신규 테이블: `review_import_batches`, `review_import_rows`, `review_import_verifications`. 원본 파일 바이너리는 보관하지 않고 파일명·해시·원본 행 필드·확인 이력을 DB에 저장한다. 현재 프로젝트의 운영 `ddl-auto: update`가 새 테이블을 생성한다. 자동 DDL을 끈 환경은 같은 엔티티 스키마를 사전에 반영해야 한다. 이 기능에는 기존 데이터 변환이 없다.

파일 업로드 상한은 애플리케이션 5MB / 요청 6MB다. 배포 저장소의 `nginx/default.conf`에서 정확히 `/api/admin/review-imports` 경로에 `client_max_body_size 6m;`를 설정했다. 기본 1MB 제한으로 인한 413 오류를 막고 multipart 부가 데이터를 허용하며, 파일 자체 상한은 백엔드에서 5MB로 유지한다. 운영 반영 시 nginx 설정 검사 및 재시작/리로드가 필요하다. 로컬 Docker 미실행으로 nginx 실행 검사는 수행하지 못했다. 프론트보다 백엔드를 먼저 배포해야 한다. 이번 작업에서는 배포하거나 push하지 않았다.

원문에는 개인정보가 포함되므로 관리자 API에서만 조회한다. 실제 제공 파일·내용은 코드 저장소나 테스트 fixture에 넣지 않았다. 엑셀 본문은 HTML로 실행하지 않고 텍스트로 표시한다.

## 운영자가 정해야 하는 사항

- 회원번호와 사이트 학번/교번/사번 체계가 다른 경우의 공식 매핑.
- 과거 서평을 수정한 경우, 기간 밖 수정된 경우, 다른 회차에서 동일 서평을 다시 쓰는 경우의 인정 기준. 현재 중복 방지는 행사 단위이며 회차 간 인정은 관리자가 확인한다.
- 잘못 반영한 이력의 취소·정정 정책과 자료 보관 기간. 이번 기능에 자동 취소·자동 삭제는 포함하지 않았다.
- SQL에 서평 고유 ID와 최초 작성일을 추가할 수 있으면 원본 추적과 기간 판단을 더 정확하게 할 수 있다. 현재 8열 양식은 그대로 지원한다.
